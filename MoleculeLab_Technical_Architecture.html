02 / ARCHITECTURE
1. Presentation Tier (Frontend)
Built with Next.js 16 (App Router), React 19, and TypeScript for a snappy, type-safe browser experience.
  • Client & Server Components: Instant page loads with zero layout shift.
  • 3Dmol.js WebGL Canvas: Hardware-accelerated 360° molecular rendering.
  • Recharts Visualization: Dynamic distribution histograms & property scatter plots.
  • Glassmorphic UI: Custom CSS variables, dark cyber theme, zero heavy UI frameworks.
  • Strict Type Contracts: TypeScript interfaces strictly mapped from backend schemas.
2. Service & API Tier (Backend)
FastAPI asynchronous web framework in Python 3.14 delivering high-concurrency REST endpoints.
  • Pydantic v2 Schemas: Microsecond JSON validation and serialization.
  • Layered Service Pattern: Routers delegate logic to decoupled services (chemistry, studio, molecule).
  • Standardized Errors: Structured error envelopes with clear scientific explanations.
  • CORS & Security: Fine-grained CORS for local development and cloud deployments.
  • Auto-Generated Docs: Interactive Swagger UI automatically available at /docs.
3. Computation & Data Tier
High-performance C++ chemistry engine combined with an ACID-compliant relational database.
  • RDKit 2026 C++ Engine: Native SMILES parsing, canon, and 2D vector depiction.
  • 3D Conformer Generator: ETKDGv3 distance geometry + MMFF94 force field.
  • SQLAlchemy 2.0 ORM: Typed relational repository with B-tree query indexes.
  • Alembic Migrations: Version-controlled, reproducible schema migrations.
  • Curated 1,338 Molecules: Seeded from PubChem and ChEMBL with provenance.

Why Chosen: First-class RDKit scientific support + native asynchronous execution.

Why Chosen: The global standard cheminformatics library used by top pharmaceutical labs.

04 / BACKEND CODE
📁 Layered Directory Structure
Clear isolation between HTTP protocols, business algorithms, schemas, and database models.
# backend/app directory layout ├── api/v1/endpoints/ # HTTP Routers (molecules, studio, export...) ├── services/ # Pure business logic (RDKit, physics, search) │ ├── chemistry.py # SMILES parsing, canon, descriptors │ ├── studio_service.py # ETKDGv3 3D conformer & MMFF94 │ ├── molecule_service.py # Database queries, pagination, search │ └── import_service.py # CSV validation & quality reporting ├── schemas/ # Pydantic v2 data validation schemas ├── models/ # SQLAlchemy ORM table definitions └── core/ # App configs, database engine & settings
  • Decoupled Routers: Endpoint handlers only handle HTTP status codes; zero chemistry logic inside routes.
  • Testability: Services can be tested independently in unit tests without starting a web server.
🔄 End-to-End Request Pipeline
Trace of a real request: POST /api/v1/studio/conformer
  • Step 1 (HTTP & Validation): Client sends JSON with SMILES. FastAPI passes payload to ConformerRequest Pydantic model. If invalid, returns 422 Unprocessable Entity immediately.
  • Step 2 (Service Invocation): Router calls studio_service.build_3d_conformer(smiles, optimize=True).
  • Step 3 (Chemistry C++): RDKit creates molecular graph, adds explicit Hydrogens (Chem.AddHs), runs ETKDGv3 distance geometry, and relaxes structure using MMFF94 force field.
  • Step 4 (Property Calculation): Derives partial atomic charges (Gasteiger) and computes minimized energy in kcal/mol.
  • Step 5 (Serialization): Converts molecule to standard SDF/MOL block and returns typed ConformerResponse JSON to client.

05 / CHEMISTRY CODE
🔬 SMILES Parsing & Canonicalization
SMILES strings are parsed defensively to catch syntax and valence errors before calculation.
def parse_smiles(raw: str) -> Optional[Chem.Mol]: trimmed = (raw or "").strip() if not trimmed: return None try: return Chem.MolFromSmiles(trimmed) except Exception: return None def canonical_smiles(mol: Chem.Mol) -> str: # Deterministic Morgan algorithm ordering return Chem.MolToSmiles(mol, canonical=True)
  • Normalizes Variations: Converts OCC and CCO into identical canonical strings.
  • Defensive 2D Vector Depiction: Uses MolDraw2DSVG to generate crisp, scalable SVG drawings on the fly.
📐 The 5 Calculated Physicochemical Descriptors
Stored at full double-precision floating point, rounded strictly in presentation layer.
def calculate_descriptors(mol: Chem.Mol): # Isolated try/except blocks prevent cascade failures return { "molecular_weight": float(Descriptors.MolWt(mol)), "logp": float(Crippen.MolLogP(mol)), "hbd": int(Lipinski.NumHDonors(mol)), "hba": int(Lipinski.NumHAcceptors(mol)), "tpsa": float(Descriptors.TPSA(mol)) }
  • MolWt (g/mol): Accurate mass derived from atomic weights.
  • LogP (Crippen): Atom-contribution estimate of lipophilicity.
  • HBD / HBA: Hydrogen bond donor/acceptor counts (Lipinski Rule of 5).
  • TPSA (Å²): Polar surface area predicting cell permeability.

06 / 3D PHYSICS
⚛️ The 4-Stage 3D Conformer Pipeline
Mathematical and physical algorithms running inside build_3d_conformer().
# 1. Add explicit Hydrogens for physical realism mol_h = Chem.AddHs(mol) # 2. Distance Geometry (ETKDGv3) Embedding params = AllChem.ETKDGv3() params.randomSeed = 42 AllChem.EmbedMolecule(mol_h, params) # 3. MMFF94 Molecular Mechanics Force Field Optimization mp = AllChem.MMFFGetMoleculeProperties(mol_h) ff = AllChem.MMFFGetMoleculeForceField(mol_h, mp) ff.Minimize(maxIts=500) min_energy = ff.CalcEnergy() # in kcal/mol # 4. Compute Gasteiger partial atomic charges AllChem.ComputeGasteigerCharges(mol_h)
📐 Geometry Derivations & Output
Real-time bond length, valence angle, and standard computational chemistry format exports.
  • 3D Euclidean Distance: \(d = \sqrt{(x_2-x_1)^2 + (y_2-y_1)^2 + (z_2-z_1)^2}\) for measuring bond lengths in Ångströms.
  • Valence Angle Derivation: Computes the vector dot product between adjacent chemical bonds to measure precise bond angles.
  • SDF/MOL Block Generation: Chem.MolToMolBlock(mol_h) serializes atomic (X,Y,Z) coordinates, bond connections, and partial charges into an industry-standard format.
  • Dual Force Field Support: If MMFF94 parameters are missing on complex metal centers, code automatically falls back to UFF (Universal Force Field).

07 / DATABASE
🗄️ Relational Schema (`models/molecule.py`)
Designed using SQLAlchemy 2.0 ORM with indexed lookup columns.
  • Primary Keys & Identity: id (Primary Key), name (Indexed), canonical_smiles (Indexed), formula, inchi_key.
  • Precomputed Descriptors: molecular_weight (Float), logp (Float), hbd (Int), hba (Int), tpsa (Float).
  • Scientific Provenance: Stores calculation_timestamp, rdkit_version, and dataset_origin on every record.
  • Cross-Database Dialect: Tested on SQLite for zero-setup local dev; 100% compatible with PostgreSQL via SQLAlchemy.
🌱 Alembic Migrations & Data Seeding
Zero schema drift and idempotent dataset population (scripts/seed_db.py).
  • Alembic Migration Scripts: Schema alterations are committed as Python migration files; reproducible with alembic upgrade head.
  • 1,338 Real Molecules Seeded:
    • 181 Educational Common Compounds (Aspirin, Caffeine, Amino Acids from PubChem).
    • 1,157 Bioactive Molecules (ChEMBL curated database).
  • Idempotent Seeder: Checks existing canonical SMILES to avoid duplicate records on multiple executions.
  • Data Integrity: Missing properties in raw files are recalculated on the fly via RDKit rather than left blank.

10 / DATA PIPELINES
📥 CSV Import & Quality Engine (`import_service.py`)
Never blindly inserts user files: validates every single row before touching the database.
  • Smart Header Detection: Tolerates case differences (smiles, SMILES, Canonical_Smiles, Name).
  • Syntax & Valence Verification: Passes each row through RDKit's Chem.MolFromSmiles to detect corrupted bonds or invalid valences.
  • Quality Error Categorization: Distinguishes INVALID_SMILES, DUPLICATE_SMILES, and SYNTAX_ERROR.
  • Descriptor Re-derivation: Ignores user-supplied values in the file and re-derives all 5 descriptors using our verified RDKit engine.
  • Detailed Quality Audit: Returns total rows, accepted count, rejected count, and specific line-by-line error messages.
📤 Reproducible Scientific Export (`export_service.py`)
Adhering to FAIR (Findable, Accessible, Interoperable, Reproducible) data standards.
  • Filtered Export: Users can download subsets matching active filters (e.g., MW < 500, LogP < 5).
  • Provenance Headers: Prefaces CSV files with scientific metadata: export timestamp, RDKit version, and calculation methods.
  • Full Floating-Point Precision: Disables lossy UI rounding to maintain scientific reproducibility in downstream analysis (Excel, Python, R).
  • Standard Identifiers: Canonical SMILES, Formula, InChI Key, PubChem CID, ChEMBL ID, and descriptors.

11 / DEFENSIVE CODE
🛡️ Chemistry Edge Cases Handled
Anticipating chemical and algorithmic edge cases in production.
  • Hypervalent Atoms (e.g. 5-bond Carbon): Intercepts RDKit C++ exceptions gracefully and returns friendly "Valence violation" error messages.
  • Stereochemistry & Chiral Centers: Preserves Cis/Trans slashes (/, \) and chiral tags (@, @@) during canonicalization.
  • Fault Isolation: Descriptors calculate in isolated try/except blocks; an issue in LogP never cancels MolWt or TPSA.
  • Null vs Zero Truth: Missing values are stored strictly as None/null. We never replace unknown data with 0.0.
🧪 Automated Testing Suite (pytest + httpx)
Over 40 comprehensive backend tests verifying system contracts.
  • Chemical Accuracy Unit Tests: Validates descriptor outputs against standard compounds (Caffeine, Aspirin, Ethanol).
  • 3D Conformer Tests: Verifies ETKDGv3 embedding, MMFF94 convergence, and atomic charge calculations.
  • API Integration Tests: Uses httpx.AsyncClient to test all REST endpoints under concurrent load.
  • Negative Testing: Asserts that malformed JSON, empty SMILES, and nonexistent IDs return structured 400/404/422 responses.

12 / VIVA GUIDE 1
❓ Q1: Why FastAPI over Flask / Django?
What to say to Sir:
  • "Sir, we selected FastAPI because of its native asynchronous async/await support, which prevents thread blocking during heavy chemistry calculations."
  • "Furthermore, FastAPI uses Pydantic v2 written in Rust for schema validation, which is up to 300% faster than traditional web frameworks."
  • "It also generates automatic interactive OpenAPI documentation at /docs, streamlining frontend integration."
❓ Q2: How does 3D conformer generation work?
What to say to Sir:
  • "Sir, we use a 2-stage computational physics pipeline:"
  • "First, ETKDGv3 uses distance geometry and experimental crystal torsion knowledge to embed initial 3D coordinates."
  • "Second, MMFF94 (Merck Molecular Force Field) treats atoms as spheres and chemical bonds as springs, performing iterative gradient descent to minimize steric clash and potential energy."
❓ Q3: Why calculate chemistry on the backend?
What to say to Sir:
  • "Sir, RDKit is a native C++ computational chemistry engine. Running it in the browser would require a 50MB+ WebAssembly bundle that would crash mobile devices."
  • "Running calculations on the backend provides a single source of truth, ensuring identical results across search, comparison, and export."
  • "It also prevents client-side tampering with calculated scientific data."

13 / VIVA GUIDE 2
❓ Q4: What is SMILES Canonicalization?
What to say to Sir:
  • "Sir, a chemical molecule can be written in many valid SMILES strings (e.g., ethanol can be 'CCO' or 'OCC')."
  • "Canonicalization runs a deterministic graph invariant algorithm (Morgan algorithm) that numbers atoms identically regardless of input order."
  • "This guarantees that identical chemical structures always produce the exact same canonical string for database deduplication."
❓ Q5: How is the database organized?
What to say to Sir:
  • "Sir, we use SQLAlchemy 2.0 ORM with SQLite and Alembic migrations."
  • "The molecules table stores structural identifiers, 5 precomputed descriptors, and provenance metadata (timestamp, RDKit version)."
  • "We placed B-tree indexes on canonical_smiles and name to maintain O(log N) lookup speeds."
  • "The system can switch to PostgreSQL with a single configuration string."
❓ Q6: How do frontend & backend communicate?
What to say to Sir:
  • "Sir, they communicate via a decoupled RESTful API using JSON payloads."
  • "Frontend TypeScript interfaces strictly mirror backend Pydantic models, eliminating type mismatch errors."
  • "Because the backend is completely decoupled, we could easily add a mobile app or CLI tool that uses the exact same API endpoints."
